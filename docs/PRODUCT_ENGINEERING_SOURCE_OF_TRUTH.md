# LinkedIn Authority — Product / Engineering Source of Truth

Last verified: 2026-09-21

## Product boundary

LinkedIn Authority turns GitHub engineering work into evidence-backed, editable LinkedIn drafts:

> You build. LinkedIn Authority helps you tell the story of what you built.

It does not publish to LinkedIn, automate engagement, send outreach, or provide official LinkedIn reach/engagement analytics. Automation creates drafts awaiting human review.

Every product page is part of the same trustworthy workflow: it must have a clear job, expose real product state, guide the user toward evidence-backed drafts, and avoid implying capabilities that are not enforced server-side.

### Page-surface hardening evidence

The onboarding flow now exposes an intentional welcome step before the GitHub/public-repository choice. Template cards are keyboard-selectable and template operations show translated inline recovery. Draft copy, repository-detail copy, and the public Live Demo copy actions only record success after the clipboard promise resolves; clipboard failures remain visible as recoverable inline errors, and the active editor also keeps refinement/hashtag failures inline without changing the text. The floating help surface now provides localized German controls plus accessible expanded/collapsed FAQ state, and Settings local session-log messages now follow the selected locale instead of exposing English-only operational copy; successful account exports now confirm the download in-page. Commit-only analysis no longer fabricates an optional link note when no link evidence was returned. These contracts are covered by the page/component tests and the browser journey.

### Bundle-loading evidence

The public/auth shell no longer imports Firestore synchronously from Firebase config. Authenticated settings, posts, drafts, and onboarding persistence use the shared on-demand Firestore loader, and the production build keeps Firestore in a separate lazy chunk. The ineffective dynamic/static import warning is gone; the remaining Firestore chunk-size warning is tracked as a dependency-size follow-up.

### API boundary hardening

All JSON requests now pass through route-aware early `Content-Length` limits before parsing (`64KB` for public demo, `128KB` for authenticated AI endpoints, `32KB` for account/automation/integrations/events/cron) and a `256KB` parser ceiling for chunked or unknown-length bodies. Production smoke verifies oversized demo and authenticated AI requests receive `413` before any repository, auth, or AI work. The public demo also maps provider failures to localized safe messages and records only coarse failure reasons, never raw backend error text or submitted repository URLs.

Unhandled API/provider failures are also logged using bounded error names and request method/path only; raw provider messages, stack traces, request bodies, bearer tokens, and generated content are not emitted by the global, AI, demo, deep-scan, cron, or repository-fetch error logs.

Dependency security was rechecked with `npm audit`: **0 vulnerabilities** after conservative patch-level remediation. `@google-cloud/firestore` is declared explicitly because the production server uses Firebase Admin Firestore even though Firebase Admin exposes it as an optional dependency; this prevents a clean install from passing typecheck while failing at runtime. `package.json`, `.nvmrc`, CI, and preflight now agree on Node 22+ so the Firestore/Firebase runtime is not silently deployed under Node 20. Firebase App Hosting runtime selection remains a manual deployment setting and must be compatible with this engine constraint. App Hosting secrets are runtime-only; the build does not receive Gemini, GitHub credential, signing, or cron secret values. Closed Beta also keeps idle instances at zero and caps the backend at three instances as an operational cost ceiling.

## Security transition

New GitHub connections send the credential once to an authenticated server endpoint. The server validates it with GitHub and stores an AES-256-GCM encrypted record using `GITHUB_CREDENTIAL_ENCRYPTION_KEY`; AI and cron routes resolve credentials server-side. The credential is not included in AI request bodies, telemetry, or client writes. Production still requires:

1. Generate and securely provision a 32-byte base64 encryption key.
2. Run `npm run migrate:github-credentials` as a dry-run, review its redacted candidate list, then explicitly opt into commit and legacy-field removal only after provisioning the key and recording a rollback plan; do not rotate production credentials automatically.
3. Verify least-privilege GitHub OAuth scopes and private-repository opt-in.

The operator checklist for these manual production gates is maintained in `docs/operations/CLOSED_BETA_RUNBOOK.md`.
